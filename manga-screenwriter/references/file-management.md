# 输出内容的文件化管理

## 项目定位与边界

- 用户给出项目目录时使用该目录；给出既有项目记录时使用其所在根目录。
- 未指定时，先检查当前工作区的`编剧项目/`。只有一个明确匹配项目可直接接续；存在多个且无法由标题或上下文确定时，只询问使用哪个项目。
- 新项目默认在`<当前工作区>/编剧项目/<项目名>/`建立，名称暂未定可使用“未命名漫剧”，检查无同名项目后使用；发生冲突则采用不覆盖的数字后缀。聊天说明所选路径，不把目录名视为已确认剧名。
- 若有旧版散落材料，先读并建立索引，可引用其现有位置；不擅自移动、删除、覆盖或重命名用户文件。确认状态无证据时标待确认，不要求重创已经有效的内容。
- 只在实际创作、修订或用户要求保存时写文件。只读审核可保存报告，但不能因此改正文。不要预建80个空白正文文件或未进入阶段的空目录。
- 无文件工具或路径不可写时，提供未保存成果和可复制快照，明确“未落盘”；不得声称已存储或已完成文件化交付。

## 最小目录与文件职责

以下为默认命名，已有项目布局合理时沿用，并在项目记录中映射。所有集数用三位数便于排序；目录按实际交付需要创建。

```text
<项目根>/
  项目记录.md
  状态仓.md
  01-项目定位.md
  02-全剧结构.md
  03-分集大纲/
    总览-001-080.md
    详细大纲-001-010.md       # 每批10集，共8批
  04-剧本正文/
    第001集.md               # 一集一文件，每轮仍交付连续5集
  05-批次附录/
    附录-001-005.md          # 检查表、场景管理表、本批连续性快照
  06-审核/
    审核-001-005-v001.md     # 范围按实际材料，可为阶段或全剧
  07-下游交接/
    交接-001-005-v001.md     # 仅用户请求交接时创建
  历史版本/
    <修订编号>/<原相对路径>   # 仅在修订已有有效内容时保存旧版
```

`项目记录.md`是唯一进度与当前有效文件索引，使用[项目记录模板](../assets/project-record.md)建立。每条索引记录路径、内容版本、范围、状态、依据版本和确认依据；不要依赖文件修改时间判断批准或有效性。

`状态仓.md`按原规范第2节保存完整当前快照，至少区分：已确认设定引用、未来计划、正文已发生事实、角色与关系当前状态、世界规则及知情证据、时间空间、伏笔、情绪与悬念、唯一主付费卡点、待决项及待修复范围。固定小传只引用01文件，避免多份正文设定互相漂移。新增事实保留集—场与正文版本；未来大纲只更新计划。

01与02文件分别承载Round 1、Round 2成品；03承载Round 3；04只放每集正文；05承载原7.4的独立附录；06承载审核；07不生成视频提示词。正文的文件级版本与状态由项目记录管理，不把管理字段混进正文计数。

## 首次创建

1. 根据本轮实际材料填项目记录；已有用户确认可记录来源，不伪造日期、版本或认可语句。
2. 保存本轮阶段成果和状态仓初版。尚未确认的角色、规则与故事事件分别列为待决候选或计划，不混入已确认设定和正文事实。
3. 项目记录登记待确认成果及下一步决定点。只建立本轮需要的文件，不把空模板称为创作完成。

## 每轮写入与接续

1. **先读**：项目记录→状态仓→已确认上游→本批大纲→必要的相邻正文。用户说“继续”时按原0.5选择合法步骤。
2. **核对**：索引范围与实际文件一致，内容完整、版本匹配且无阻断；一个文件存在不代表其中集数完整。不一致时先标记并修复记录，不能猜测已完成集数。
3. **产出**：保存本轮成品。Round 3每次一份10集详细大纲；Round 4每次5个逐集正文文件加一份批次附录。定点修订只改受影响集，不强迫重写五集。
4. **检查**：实际读取落盘内容，核对范围、场号与对应质量项。按H3统计单集剧本全文字数，并按0.3检查开场抓力。
5. **同步**：更新状态仓、检查表、修订记录及受影响索引。最后更新项目记录的完整完成范围和下一步，不在成品保存前提前宣告完成。
6. **汇报**：聊天给本轮文件链接、完成范围、检查结论和下一步，待确认时列明用户需确认的成果。默认不重复粘贴已落盘的全部长文。

批次截断或写入失败：已落盘部分可保留，项目记录写明原批次、最后完整集/场、缺失范围、待修复项。下一轮先补齐同一批次；不得从“已有部分文件”推断整批完成。状态仓若已同步到完整单集，明确该截至位置与批次未完成状态。

## 确认、版本与修订

- 内容版本从v001开始，只有内容变更才递增；确认状态单独更新，不为“确认”复制一套相同内容。状态采用“未完成／待确认／工作版本／已确认／待修复／已取代”，按真实情况选择。
- 确认依据记录用户原意、覆盖成果和版本；已完成、已自检、已保存均不等于已确认。单独“继续”按0.5处理。
- 修改既有有效内容前，把原文件保存到唯一修订编号目录，保留相对路径，不覆盖已有历史。当前有效路径稳定，历史版不参与默认续写。
- 已确认上游变更先按2.5给影响摘要；用户明确授权的修改范围无需重复审批，超出范围的重大影响仍需确认。只要求诊断或审核时，将替换候选留在报告中。
- 修订记录注明原因、旧/新版本、受影响集—场、相关伏笔及知情变化、验证结果和未修复项；同步状态仓和必要的上下游文件。不要只改正文而保留失效的计划或角色认知。
- 若跨文件修订中断，在项目记录标记所有未同步范围“待修复”，完成前不续写新正文。没有新增失败或风险时不重复扩大检查。
- 不自动删除历史版、不擅自提交Git、不创建外部数据库或云服务。已有Git不能替代明确的当前有效版本与确认记录。

## 文件化验收

交付前核对：文件可读、相对链接可解析、集数连续且无重复、状态仓截至位置与正文匹配、未来伏笔没有登记为实际回收、待确认及待修复状态真实、下一步符合门控。第80集完成后将下一步设为Round 5；全剧结案必须有覆盖80集实际正文的审核依据。
